# Win on tokens and turns, not accuracy

Playwriter can't credibly claim to be "more accurate" than other browser tools, because no benchmark shows that the tool changes success much once the model is fixed. It can credibly claim to be cheaper, faster and more capable, and several open harnesses already exist to measure that. The key evidence is Browser Use's matched eval of coding-agent browser tools on 100 BU Bench V2.1 tasks. With the same agent, model, judge and cloud browser, Playwright MCP, Chrome DevTools MCP, agent-browser and Browser Harness scored 56 to 61 points, with overlapping confidence intervals. Median input tokens ranged from **2.1M to 6.7M** and median tool calls from **42 to 67.5** ([browser-harness README](https://github.com/browser-use/browser-harness)). Playwriter is not in that table, or in any leaderboard we found. So the first move is to add a Playwriter row to that eval, which gives directly comparable numbers next to four competitors. The second is to publish the first "tokens vs number of items" scaling curve for browser tools, where one script that loops should beat N tool calls. The third is a capability suite that nobody has published: hard UI patterns, the user's own logged-in browser, stealth on a real profile, and the cost of attaching to Chrome instead of launching it. Saturated success leaderboards such as WebVoyager (top score 99.19%) are worth one later run for name recognition, not as the headline ([Steel WebVoyager](https://leaderboard.steel.dev/leaderboards/webvoyager)).

## Competitors publish almost nothing comparable, and one eval already sets the bar

There are two kinds of tools. **Autonomous agents** (browser-use, Magnitude, Skyvern, Surfer, Notte, Operator, Stagehand's agent) compete on success leaderboards such as WebVoyager, Online-Mind2Web, WebArena and BU Bench. **Coding-agent tools**, which is Playwriter's category, publish almost no task-success numbers at all. Playwright MCP, Playwright CLI, Chrome DevTools MCP, agent-browser, BrowserMCP, mcp-chrome and BrowserTools MCP make only qualitative "token-efficient" or "fast" claims in their READMEs ([playwright-mcp](https://github.com/microsoft/playwright-mcp), [chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp), [agent-browser](https://github.com/vercel-labs/agent-browser), [BrowserMCP](https://github.com/BrowserMCP/mcp)). Even Microsoft gives no numbers when it recommends Playwright CLI over MCP for coding agents because the CLI avoids "loading large tool schemas and verbose accessibility trees into the model context" ([playwright-cli](https://github.com/microsoft/playwright-cli)).

Two things in this table shape the strategy. First, in the only matched comparison, **every paired score difference against Browser Harness had a 95% CI that included zero**. Tokens, cost and tool calls separated the tools; success did not ([browser-harness README](https://github.com/browser-use/browser-harness)). Second, the eval left out exactly the setups Playwriter's users care about: Claude Code, Playwright CLI and Claude in Chrome were not measured, and every tool ran in "a fresh cloud browser every time, not your logged-in Chrome" ([Browser Use blog](https://browser-use.com/posts/best-mcp-servers-to-control-a-browser)). Browser Use wrote the eval and its own tool won on tokens, so an independent rerun with a Playwriter row is useful to everyone. dev-browser-eval is the other template that matters. It runs `claude -p` headless with one browser plugin enabled per method, 3 runs each, on a local CRUD app. dev-browser finished in **3m53s for $0.88 in 29 turns**, against **4m31s, $1.45 and 51 turns** for Playwright MCP and **12m54s, $2.81 and 80 turns** for Claude's Chrome extension ([benchmark-comparison.md](https://github.com/SawyerHood/dev-browser-eval/blob/main/benchmark-comparison.md), [benchmark.ts](https://github.com/SawyerHood/dev-browser-eval/blob/main/scripts/benchmark.ts)).

## Standard success benchmarks are saturated, so rank them by credibility per dollar

WebVoyager has 643 live tasks and its top score is 99.19%. Teams now drop "currently impossible" tasks and use different judges, and Steel warns that rows "are not directly comparable" ([Steel WebVoyager](https://leaderboard.steel.dev/leaderboards/webvoyager)). Online-Mind2Web (300 tasks, 136 sites, o4-mini WebJudge with 86% human agreement) has the same problem: the top is 97.0%, and that entry used a custom judge ([Online-Mind2Web README](https://github.com/OSU-NLP-Group/Online-Mind2Web), [Steel](https://leaderboard.steel.dev/leaderboards/online-mind2web)). A Playwriter run on either would show a small or zero success gap. It is worth doing only for name recognition and a Steel leaderboard row. The precedent helps: two of the top three WebVoyager entries are "Claude Code + a browser CLI/MCP", which is Playwriter's exact shape, and their harnesses are public.

The benchmarks that matter more for Playwriter have one of three properties: deterministic scoring, efficiency metrics, or a ready-made comparison against tools. **WebArena-Verified** audited all 812 tasks, replaced LLM judging with deterministic checks on agent output and network traces, and has a 258-task hard subset ([webarena-verified](https://github.com/ServiceNow/webarena-verified)). **WebChoreArena** adds 532 tedious "Massive Memory" and "Calculation" chores on the same self-hosted sites, which is exactly the loop-and-aggregate work where scripts should win ([arXiv 2506.01952](https://arxiv.org/abs/2506.01952)). **Odysseys** is the only benchmark that treats efficiency as a first-class metric (rubric score per step) ([Odysseys](https://odysseys-website.pages.dev/)). **Stagehand evals** already runs Claude Code, Codex and Cursor as harnesses over WebVoyager, Online-Mind2Web, WebTailBench, Odysseys and HardBench, and reports $ and seconds per task. It does not yet have a pluggable "playwriter" tool surface ([Stagehand evals README](https://github.com/browserbase/stagehand/blob/main/packages/evals/README.md), [harness contract](https://github.com/browserbase/stagehand/blob/main/packages/evals/docs/harness-contract.md)). **WebGames** is 150 client-side challenges with password-verified success that run locally for almost nothing ([WebGames](https://github.com/convergence-ai/webgames)).

| Rank | Benchmark | What it proves for Playwriter | Cost / effort |
|---|---|---|---|
| 1 | BU Bench V2.1 coding-agent eval (bu2-001..100) | Direct row next to Playwright MCP, DevTools MCP, agent-browser, Browser Harness | Low: published medians are $0.04-0.10 model cost per task; needs CDP to the same cloud browser ([benchmark](https://github.com/browser-use/benchmark)) |
| 2 | Custom scaling suite (extended dev-browser-eval) | Script beats N tool calls; tokens and turns vs N | Medium: our fixtures, deterministic checkers |
| 3 | WebChoreArena subset (10-20 tasks) | Third-party, deterministic version of the scaling claim | Medium: WebArena Docker setup |
| 4 | WebArena-Verified Hard sample (50-100) | Credible, reproducible success parity | Medium-high: heavy Docker (GitLab, map) |
| 5 | WebGames (150) | Hard interactions (drag, scroll, right-click), cheap | Very low |
| 6 | Stagehand evals with a Playwriter tool adapter | Reuse their judges, cost accounting and harnesses | Needs fork or upstream PR |
| 7 | Online-Mind2Web (50-100 sample) | Standard live benchmark; real Chrome fits | Low judge cost; live drift |
| 8 | WebVoyager via omxyz/webvoyager | Recognition and a Steel row | Saturated; only matters near 99% |

BrowseComp, GAIA and Mind2Web 2 mostly measure model research skill (BrowseComp's top entries are just models at 90-92%), so a browser tool can't show a difference there ([Steel hub](https://leaderboard.steel.dev/)). WebBench WRITE tasks need logins and 2FA on hundreds of live sites, and human evaluation cost about **$3,000 per agent** ([Skyvern blog](https://www.skyvern.com/blog/web-bench-a-new-way-to-compare-ai-browser-agents/)).

## One script that loops should beat N tool calls, and nobody has plotted it

The mechanism behind Playwriter's speed claim has good primary evidence outside browsers. Anthropic's code-execution-with-MCP post cut a Drive-to-Salesforce workflow from **150,000 to 2,000 tokens (98.7%)** by letting the model filter data in code ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)). Its Programmatic Tool Calling cut average tokens from **43,588 to 27,297 (37%)** and says batching 20+ calls in one code block can "eliminate 19+ inference passes" ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)). Research points the same way. CodeAct reports up to 20% higher success with code actions ([arXiv 2402.01030](https://arxiv.org/abs/2402.01030)). API-plus-browse agents gain 24 points absolute on WebArena ([arXiv 2410.16464](https://arxiv.org/abs/2410.16464)). AWM and WALT reach higher success with fewer steps ([arXiv 2409.07429](https://arxiv.org/abs/2409.07429), [arXiv 2510.01524](https://arxiv.org/abs/2510.01524)). But none of these papers measures tokens, $ and wall time for script-based vs per-action browser control on the same tasks, and no published benchmark plots cost against the number of items. That gap is Playwriter's best opening.

The useful split is between three costs: tool-schema overhead, the bytes each step returns (snapshots), and the number of inference passes. Playwright CLI and agent-browser reduce the first two but still need one shell call per action. Playwriter and dev-browser can also collapse the third. dev-browser-eval only repeated its core action five times ("add 5 games"), and that was already enough for a 43% turn reduction over Playwright MCP ([benchmark-comparison.md](https://github.com/SawyerHood/dev-browser-eval/blob/main/benchmark-comparison.md)). Our hypothesis is that turns for script tools stay roughly flat as N grows, while per-action tools grow linearly. Tokens should grow faster than linearly for per-action tools, because the full history is re-sent every turn. This is not yet measured, and the suite below is designed to test it honestly.

| Task | Scales with N by | Checker |
|---|---|---|
| T1 Paginated table scrape to JSON | pages and rows | exact JSON match |
| T2 List page, then N detail pages, return sum/average | navigations held in memory | numeric equality |
| T3 Bulk form entry of N records from a CSV (dev-browser-eval scaled up) | N × fill + submit | DB query |
| T4 Infinite scroll, collect N items | scroll + read cycles | exact set match |
| T5 Conditional bulk edit across pages | per-row logic | DB query |
| T6 Control: log in, change one setting (N=1) | none; per-action tools may tie or win | DB query |

Run each at N = 1, 10, 50 and 100, and plot tokens, $, turns, wall time **and success** against N. Per-action agents often stop early or skip items on long lists, which is WebChoreArena's "Massive Memory" failure mode. Keep T6 even if Playwriter loses it, because it makes the curves believable. For micro-latency, copy dev-browser's method (median of 9 runs: empty script, get page + title, snapshot, screenshot, cold start) so both tools can be compared on the same table ([dev-browser](https://github.com/SawyerHood/dev-browser)).

## The real-Chrome advantage is unmeasured everywhere: stealth, logins, hard UI, resources

Every stealth benchmark tests fresh or cloud browsers, and none tests the user's own running Chrome. **Stealth Bench V1** (71 sites from 300,000 production block events, LLM judge only checks "was it blocked") ranks Browser Use Cloud 81%, Anchor 77%, Kernel 67%, Steel 47%, Browserbase 42% and Hyperbrowser 40%. Its datacenter controls show headless Chromium at **2%** and headful at **50%** ([Browser Use blog](https://browser-use.com/posts/stealth-benchmark)). The runner already has `local_headful` and `local_headless` providers, so a `playwriter` provider is a small adapter ([browser-use/benchmark](https://github.com/browser-use/benchmark)). Halluminate **BrowserBench** (292 sites, scored as stealth failure rate) is public on GitHub and HF ([Halluminate](https://halluminate.ai/blog/browserbench)). Its failure rates (1.7-6.8%) must never be put next to Browser Use's success rates (70-85%) because they measure different things. One honest caveat: chrome.debugger attaches CDP to the tab, and detectors look for CDP side effects such as the `Runtime.enable` leak that patchright and rebrowser-patches fix. Add a fingerprint check (bot.sannysoft.com, the rebrowser detector) next to the site results ([techinz/browsers-benchmark](https://github.com/techinz/browsers-benchmark)). Also run Playwriter from a clean profile on the same IP, so the profile's reputation effect is separate from the tool.

**Logged-in tasks** are an open niche. WebArena and REAL use cloned sites with pre-made accounts, Online-Mind2Web excludes logins, and the only published numbers for agents in a real logged-in browser are Anthropic's prompt-injection rates. For example, Opus 4.5 went from 8.0% to 1.4% attack success with safeguards under a Best-of-N attacker ([Anthropic](https://www.anthropic.com/research/prompt-injection-defenses)). Playwriter can define the first capability set here, with read-mostly tasks on non-Google services (GitHub notifications, X bookmarks, an order history). Score it as "completed with no login step and no human help", and compare against Playwright MCP `--extension`, Chrome DevTools MCP `--autoConnect` and agent-browser `--auto-connect`, which are the competitors' own logged-in modes ([Browser Use blog](https://browser-use.com/posts/best-mcp-servers-to-control-a-browser)). REAL Bench offers a reproducible version: deterministic, pre-logged-in clones of 11 sites, with "bring your own system" black-box support ([realevals.ai](https://www.realevals.ai)). Safety is the obvious objection. Publishing a small hidden-DOM injection test, or WASP ([arXiv 2504.18575](https://arxiv.org/abs/2504.18575)), shows that attack success depends on the model, not the transport layer.

**Hard-UI patterns** have practice sites but no per-tool results. WebGames' best AI scored 43.1% against 95.7% for humans ([arXiv 2502.18356](https://arxiv.org/abs/2502.18356)). The-internet.herokuapp, UI Testing Playground and Expand Testing each isolate one pattern per page. A 20-row pass/fail matrix would show where a full Playwright API plus raw CDP matters and fixed MCP action sets fall short: cross-origin iframe, closed shadow root, canvas drag, HTML5 drag and drop, upload, download to disk, alert/confirm/prompt, beforeunload, popup tab, native select, contenteditable, hover menu, infinite scroll, clipboard, basic auth, network interception. Browser MCP, for example, has no tool to open or switch tabs ([Browser Use blog](https://browser-use.com/posts/best-mcp-servers-to-control-a-browser)). That this matrix favors Playwriter is a hypothesis to test, and it must include Playwriter's own limits (chrome:// pages, the Web Store, other extensions).

**Resources** are a cheap, unique win. Published numbers only cover launching new browsers. A freshly launched local Chromium used about 0.5-1.4 GB RAM ([techinz](https://github.com/techinz/browsers-benchmark)). Cloud sessions took 776 ms to 7.9 s median to create, connect, navigate and release over 5,000 runs ([steel-dev/browserbench](https://github.com/steel-dev/browserbench)). Nobody has measured the marginal cost of attaching to an existing Chrome. Reuse Steel's four stages (relay connect, new page, goto, close) and techinz's process-tree RAM method against Playwright MCP's default launch, Chrome DevTools MCP and agent-browser headless.

Playwriter's own results will carry the same "vendor-run" label. The only defence is open transcripts and one-command reproduction.

## Run three benchmarks first, with one harness and strict fairness rules

**First: a Playwriter row in the BU Bench V2.1 coding-agent eval.** Use tasks bu2-001 to bu2-100, Codex CLI with GPT-6 Luna medium, web search off, the same frozen judge, the same prompt except the one line naming the tool, one run per task and no retries. This matches Browser Use's published method ([browser-harness README](https://github.com/browser-use/browser-harness)). To get the same browser, point Playwriter at a fresh Browser Use cloud browser over CDP. The repo already has a typed Browser Use `/browsers` client in `website/src/lib/browser-use.ts`, so this needs little new code. Then rerun the same 100 tasks with Claude Code, adding Playwright CLI and Claude in Chrome, to fill the gaps in their table. Headline metrics: median input tokens, tool calls, $ and minutes, with score and 95% CI shown as parity. At the published medians, model cost is a few dollars per 100-task tool run. Wall time (about 9 minutes per task) is the real cost, so run tasks in parallel on separate cloud browsers.

**Second: the scaling suite (T1-T6, N = 1/10/50/100) on a local fixture app.** Copy dev-browser-eval's harness: `claude -p "<task>" --output-format stream-json --verbose`, one browser tool enabled per run through per-method `settings.local.json` and `--mcp-config`, state reset between runs ([benchmark.ts](https://github.com/SawyerHood/dev-browser-eval/blob/main/scripts/benchmark.ts)). Read `duration_ms`, `num_turns`, `total_cost_usd` and `usage` from the final result event. Note that Claude Code calls these "client-side estimates" ([Claude Code headless docs](https://docs.claude.com/en/docs/claude-code/headless)). Compare against Playwright MCP (default and `--snapshot-mode`), Playwright CLI, Chrome DevTools MCP (default and `--slim`), agent-browser and dev-browser, all attached to the same running Chrome where the tool supports it. Add 10-20 WebChoreArena Massive-Memory/Calculation tasks as the third-party version. My rough estimate, not a measured figure: 6 tasks × 4 N values × 6 tools × 3 runs is about 430 runs and likely $500-2,000 of model spend at dev-browser-eval's $0.88-2.81 per short run. Pilot at N = 10 first and drop tools that obviously don't scale.

**Third: a capability report card.** It has four parts: the 20-pattern hard-UI matrix plus WebGames, Stealth Bench V1 with a `playwriter` provider next to `local_headful`/`local_headless` and the published cloud numbers, a 10-task logged-in set on non-Google services, and the attach-vs-launch latency and RAM table. All four are cheap and nobody else has published any of them.

The fairness rules apply to all three. Fix the model and harness and change only the browser tool. Use one prompt template. Record every competitor's version and flags. Count Playwriter's skill text as part of its context cost. Run each task at least 3 times, or use paired per-task CIs, because gaps under about 10 points are noise at 30-100 tasks. Report raw input tokens and $ separately, because prompt caching hides re-sent context. Report **cost per successful task**, not cost averaged over failures. Use deterministic checkers wherever possible. Run every tool in the same browser, and report "real profile" and "clean profile" Playwriter runs separately. Publish JSONL transcripts, per-task JSON, task revisions (BU Bench v2.1.1, WebTailBench `test_v2`), run dates and every exclusion. Do not publish decrypted BU Bench tasks, only IDs and scores ([browser-use/benchmark](https://github.com/browser-use/benchmark)). Run a second model family (GPT through Codex) before making general claims.

**Presentation.** Keep it to what the data supports. Put one chart above the fold in the README: tokens (or $) vs N items, one line per tool, with a short caption like "same success as Playwright MCP, X× fewer tokens at 100 items" and the run date. Below it, show a compact table with the BU Bench row (score with CI, median tokens, tool calls, $, minutes) next to the four published tools, with a link to Browser Use's original data. Add a ✅/❌ capability matrix for hard UI, logged-in tasks and stealth. On the website, a `/benchmarks` page should hold the interactive curves, per-task drill-down with transcripts, the full methodology and fairness list, the losses (T6, CDP detectability, pages chrome.debugger can't attach to), and a one-command reproduce script in a `benchmarks/` folder. Once a WebVoyager run via omxyz/webvoyager is done, submit it to the Steel leaderboard, which accepts PRs ([steel-dev/leaderboard](https://github.com/steel-dev/leaderboard)). Never write "most accurate" or "#1". The defensible line is "same success, a fraction of the tokens and turns, and things other tools can't do".

## Conclusion

The market has quietly settled the accuracy question. When the model is fixed, browser tools tie, so the contest has moved to cost, speed and reach. Playwriter's design advantages are multi-step scripts in one call, the user's real profile and the full Playwright API plus CDP. These are exactly the dimensions no one has measured: no scaling curve, no logged-in capability set, no stealth result for a real running Chrome, no attach-cost numbers. Measuring them first lets Playwriter set the evaluation frame instead of chasing a saturated leaderboard.

The main risk is credibility, not results. A vendor-run benchmark persuades only if it publishes its transcripts, keeps its losing control tasks, separates the real-profile advantage from the tool advantage, and invites reruns. A Playwriter row in Browser Use's own published table, run by their rules, is worth more than any number from Playwriter's own harness, because a competitor wrote the rules.
